40 TOPS급 NPU를 갖춘 PC도 구매 근거는 따로 필요하다. Microsoft는 여러 Copilot+ 기능에 이 수준의 연산 성능을 요구한다. 나는 도입 검토표에서 성능 수치보다 업무 데이터의 이동 경로를 먼저 확인한다. ([Microsoft Copilot+ 개발 지침](https://learn.microsoft.com/en-us/windows/ai/npu-devices/))

*대기열 기준일은 2026-08-27이다. 자료는 2026-09-16에 확인한 공식 문서를 기준으로 정리했다.*

## 1. 장치가 아니라 업무 기능을 선정한다

온디바이스 AI는 사용자 기기에서 모델을 실행하는 방식이다. NPU는 신경망 연산을 처리하는 전용 반도체다. TOPS는 초당 조 단위 연산 횟수를 뜻한다. 이 숫자만으로 한국어 요약의 정확도를 알 수는 없다.

Microsoft도 NPU 활용에는 전용 소프트웨어 구현이 필요하다고 설명한다. 따라서 구매 대상과 함께 사용할 앱·모델·운영체제 버전을 묶어야 한다. 기기에 NPU가 있어도 선정한 업무가 이를 사용하는지는 별도 검증 대상이다.

첫 후보는 회의록 요약이나 문서 분류처럼 범위가 좁은 업무로 잡는다. 원문 길이와 언어를 고정하고 사람이 정답을 검토한다. 장치 사양표와 업무 합격표를 따로 만드는 이유다.

## 2. 로컬 실행 범위를 데이터 경로로 확인한다

Apple Intelligence는 기기에서 처리할 수 있는 요청을 판단한다. 더 큰 연산이 필요하면 Private Cloud Compute를 사용할 수 있다. 이는 Apple이 제공하는 클라우드 처리 체계다. 브랜드에 온디바이스 기능이 있다는 사실만으로 모든 요청의 내부 처리를 보장하지는 않는다. ([Apple의 Mac AI 개인정보 보호 안내](https://support.apple.com/guide/mac-help/apple-intelligence-and-privacy-mchlfc0d4779/mac))

내가 요구사항에 넣을 항목은 입력·출력·진단 로그의 목적지다. 외부 처리가 허용되지 않는 문서는 전송을 차단한 상태에서도 시험한다. 모델 다운로드를 마친 뒤 연결을 끊고 기능별 성공 여부를 기록한다. 다만 이 시험만으로 온라인 상태의 전송 부재를 입증할 수는 없다. 공급사 문서와 통신 기록도 함께 확인한다.

클라우드 전환을 허용할 업무라면 전환 조건을 명시한다. 처리 실패 시 사용자가 다른 서비스에 원문을 붙여 넣지 않도록 승인된 대체 절차도 정한다.

## 3. 기기에 남는 데이터도 관리한다

Recall은 화면 기록을 기기에 저장하고 분석하는 Windows 기능이다. Microsoft 문서에 따르면 조직 관리 장치에서는 기본적으로 제거되어 있다. 관리자가 사용을 허용해도 화면 저장에는 사용자 동의가 필요하다. 보관 기간과 앱·웹사이트 제외 정책 일부는 Enterprise·Education 에디션에만 적용된다. ([Microsoft Recall 관리 문서](https://learn.microsoft.com/en-us/windows/client-management/manage-recall))

여기서 얻는 도입 기준은 분명하다. 로컬 저장이라는 설명과 조직의 통제 가능 범위를 함께 읽어야 한다. 문서 원본 외에 화면 기록과 검색용 데이터가 남는지 확인한다. 장치 분실, 사용자 퇴사, 재지급 시 삭제 책임자도 정한다. 관리 화면에서 정책을 설정한 뒤 실제 장치에 반영됐는지 증거를 남긴다.

아래 표는 제품 공통 사양이 아니라 내가 제안하는 검수 기준이다.

| 검수 영역 | 확보할 증거 | 도입 보류 조건 |
|---|---|---|
| 데이터 경로 | 기능별 통신 기록과 처리 위치 | 승인되지 않은 외부 전송 |
| 로컬 보관 | 암호화·보관 기간·삭제 시험 결과 | 민감 데이터 삭제 실패 |
| 조직 통제 | 운영체제별 정책 적용 결과 | 필수 정책 적용 불가 |
| 변경 관리 | 모델·앱·드라이버 버전과 재시험 결과 | 업데이트 후 업무 품질 미달 |

## 4. 구매 전에 운영 비용을 계산한다

다음은 실제 측정 결과가 아닌 시험 설계 예시다. 비식별 한국어 문서 100건을 고정한다. 숫자 누락 건수, 사람의 수정 시간, 처리 시간을 잰다. 전원 연결과 배터리 사용 조건을 나눠 시험한다. 최초 모델 준비 시간도 일상 처리 시간과 구분해 기록한다.

합격선은 기존 수작업 결과를 기준으로 업무 담당자가 정한다. 모델이나 드라이버가 바뀌면 같은 문서로 재시험한다. 복구가 불가능한 구성이라면 기능 중지와 수작업 전환 절차를 마련한다.

비용표에는 장치 추가 구매비뿐 아니라 배포·교육·지원 시간을 넣는다. 사람의 검토 시간을 뺀 순절감 시간이 양수인지 확인한다. 외부 호출이 줄어든 만큼 운영 부담이 늘 수 있으므로 실제 사용량으로 비교한다.

이번 문서 조사에서 얻은 판단은 도입 단위를 좁혀야 한다는 것이다. 다음 단계는 한 부서의 한 업무에서 위 증거를 수집하는 일이다. 데이터 경로와 관리 정책을 검증한 뒤 장치 확대 여부를 결정한다.
