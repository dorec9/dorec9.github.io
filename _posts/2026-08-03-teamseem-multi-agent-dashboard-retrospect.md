에이전트를 여러 개 돌리다 보면 지금 어떤 서브 에이전트가 무슨 태스크를 처리하는지 터미널 로그만으로는 파악하기 어렵다. TeamSeem은 이 문제를 풀려고 만든 실시간 관제 대시보드다. Antigravity(Gemini 기반 에이전트 프레임워크) 시스템에서 발생하는 서브 에이전트 생성, 태스크 처리, 메시지를 웹 화면에서 그래프와 채팅 패널로 보여준다. 이 글은 훅 연동 방식을 한 번 갈아엎은 과정과, 다이어그램에 정보를 얼마나 담을지를 두고 오간 판단을 정리한다.

---

## 프로젝트 배경과 목적

Antigravity로 멀티 에이전트 작업을 돌리면 부모 에이전트가 서브 에이전트를 위임하고, 서브 에이전트가 다시 태스크를 쪼개는 구조가 반복된다. 이 위임 관계와 진행 상황을 실시간으로 확인할 방법이 마땅치 않았다. TeamSeem은 세 가지를 목표로 잡았다.

1. 새 세션이 생기면 자동으로 감지해 UI에 포커스한다.
2. 부모-자식 에이전트 관계를 다이어그램으로 표현한다.
3. 30분 이상 유휴 상태인 세션은 자동으로 종료 처리한다.

파일시스템 와쳐(`ag-watcher.mjs`)가 로그 변화를 감지하고, 웹소켓과 Server-Sent Events로 프론트엔드에 이벤트를 밀어 넣는 구조다.

---

## 기술 스택과 선택 이유

프론트엔드는 Next.js 16 App Router에 React 19, Tailwind CSS 4를 썼다. 다이어그램은 [React Flow](https://reactflow.dev/)(`@xyflow/react`)와 Dagre로 계층 레이아웃을 잡는다. 에이전트 관계는 트리보다 방향성 그래프에 가깝다. DOM 기반으로 노드·엣지를 자유롭게 그릴 수 있는 React Flow가 커스텀 캔버스를 직접 짜는 것보다 개발 속도가 났다.

상태 관리는 Zustand로 통일했다. `agent-store`, `message-store`, `session-store`, `task-store` 4개로 도메인을 나누고 각각 테스트 파일(`.test.ts`)을 붙였다. 실시간 이벤트가 여러 스토어에 동시에 영향을 주는 구조라 스토어 단위로 리듀서 로직을 검증할 필요가 있었다.

DB는 [Prisma](https://www.prisma.io/docs) ORM 7과 better-sqlite3 조합을 골랐다. 로컬 데스크톱에서 도는 개인용 도구라 별도 DB 서버를 띄우는 대신 파일 기반 SQLite로 충분하다고 판단했다.

## 설계 판단 1: 훅 아키텍처를 한 번 갈아엎었다

초기 버전은 Claude Code의 `~/.claude/settings.json` hooks 필드를 이용했다. 이벤트가 발생하면 쉘 환경변수 `$CLAUDE_HOOK_PAYLOAD`에 페이로드가 담기고, 이를 curl로 웹훅 전송하는 방식이었다. 문제는 이 구조가 Claude Code 환경에 강하게 종속된다는 점이었다.

Antigravity로 주력 작업 환경을 옮기면서 훅 연동도 다시 짰다. `.agents/hooks.json`에 훅을 설정하고, 이벤트 발생 시 표준입력(stdin)으로 JSON 페이로드를 받아 `curl -d @-`로 stdin을 그대로 POST body에 실어 로컬 서버(`localhost:3000/api/events`)로 보내는 방식으로 바꿨다.

여기서 걸린 부분이 하나 있었다. Antigravity 페이로드에는 이벤트 타입(PreToolUse 등) 정보가 빠져 있었다. 대응은 curl 요청에 `?event=PreToolUse` 같은 쿼리 파라미터를 붙여 이벤트 타입을 직접 주입하는 방식이었다. 백엔드의 `route.ts`에서 이 쿼리 파라미터를 읽어 내부 객체의 `hook_event_name` 속성으로 채워 넣는다.

페이로드 파서(`normalize-payload.ts`)도 전면 개편이 필요했다. 기존은 스네이크케이스(`hook_event_name`, `session_id`) 기반이었는데, Antigravity는 카멜케이스(`conversationId`, `toolCall`)를 쓴다. 두 포맷을 동시에 지원하려고 시도했다가 분기 조건이 늘어나 코드가 지저분해졌다. 결국 신규 포맷 기준으로 파서를 새로 짜는 쪽을 택했다. 하위 호환을 포기하는 대신 파서 하나의 책임을 명확히 유지하는 게 유지보수에는 나았다.

## 설계 판단 2: 다이어그램에 태스크를 몇 개까지 보여줄 것인가

같은 날(2026-07-04) 커밋 로그를 보면 다이어그램 정보 밀도를 두고 방향이 두 번 바뀐 흔적이 있다. 처음에는 각 에이전트 노드 아래 모든 태스크를 다 그렸는데, 태스크가 늘어나면 화면이 선으로 뒤덮이는 문제가 생겼다. 그래서 "에이전트당 가장 관련도 높은 태스크 1개만" 렌더링하도록 좁혔다.

그런데 이번엔 반대 피드백이 나왔다. 태스크 1개만 보이니 나머지가 어디로 갔는지 알 수 없다는 것이었다. 결국 하드코딩된 단일 태스크 제한을 걷어내고, 마크다운 불릿의 들여쓰기를 기준으로 계층을 파싱해 트리 구조 전체를 그리는 방향으로 다시 바꿨다. `TaskChecklist` 컴포넌트에 인덴트 깊이로 부모-자식 관계를 추론하는 휴리스틱(정확한 파싱 대신 들여쓰기 패턴 같은 경험적 규칙으로 근사하는 방식)을 추가했다. `TaskNode` 폭을 텍스트 길이에 맞춰 동적으로 조정해 긴 태스크명이 잘리는 문제도 같이 해결했다.

정리하면 "다 보여주기 → 1개만 보여주기 → 계층 구조로 전체 보여주기"로 세 단계를 거친 셈이다. 노드 개수를 줄이는 것만으로는 가독성이 해결되지 않았고, 개수보다 구조(계층 트리)로 정보를 정리하는 편이 정보 손실 없이 화면을 정리하는 방법이었다.

같은 날 작업 중 `.gitignore` 설정 오류로 소스 파일 일부가 원격 저장소에 올라가지 않은 사고도 있었다. 로컬에서는 정상 동작하는데 clone 받은 환경에서 빌드가 깨져서 원인을 찾다 발견했다. 이후 커밋에 누락된 파일을 다시 푸시해 복구했다.

## 배운 점과 개선할 점

훅 페이로드 포맷은 프레임워크마다 다르다는 전제를 처음부터 깔고 파서 계층을 분리해뒀어야 했다. 이번엔 마이그레이션 시점에 파서를 전면 교체했지만, 애초에 정규화 계층(`normalize-payload.ts`)을 프레임워크별 어댑터 구조로 짰다면 교체 범위가 더 좁았을 것이다.

다이어그램 정보 밀도는 "적게 보여줄지 많이 보여줄지"의 이분법이 아니라 "어떤 구조로 묶어서 보여줄지"의 문제였다. 태스크 개수를 줄이는 시도(에이전트당 1개)는 정보 손실이 있었고, 계층 트리로 묶는 방식이 개수를 유지하면서도 화면을 정리하는 결과를 냈다.

`.gitignore` 오설정은 CI 단계에서 clone 후 빌드를 검증하는 파이프라인이 있었다면 바로 잡혔을 사고다. 지금은 로컬 빌드 성공만 확인하고 푸시하는데, 다음 프로젝트에는 최소한 GitHub Actions로 clone-and-build 체크를 넣을 계획이다.
